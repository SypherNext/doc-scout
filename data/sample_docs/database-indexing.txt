Database Indexing

A database index is a separate data structure that lets the database find rows matching a condition without scanning every row in the table. Without an index, looking up a single customer by email in a table of ten million rows requires reading all ten million rows, a "full table scan," because the database has no way to know where a matching row might be. An index on the email column lets the database jump almost directly to the matching rows instead.

Most relational databases implement indexes as a B-tree, a balanced tree structure where every path from the root to a leaf is the same length. B-trees keep their keys sorted, which means they support not only exact lookups ("find the row where email equals this value") but also range queries ("find every order placed between two dates") and efficient sorting, since the data is already ordered. A B-tree lookup, insert, or delete on a table of a million rows takes roughly the same handful of steps as one on a table of a billion rows, because the height of the tree grows logarithmically with the number of rows, not linearly.

An index is only useful for the columns it actually covers. A single-column index on email speeds up queries that filter by email, but does nothing for a query that filters by phone number. A composite index covers multiple columns together, such as an index on (last_name, first_name); it speeds up queries that filter on last_name alone or on both columns together, but it generally cannot be used efficiently to filter on first_name alone, because the index is sorted by last_name first. Choosing which columns to index, and in what order, is one of the most common real-world database tuning decisions.

Indexes are not free. Every index must be updated whenever a row is inserted, updated, or deleted, so a table with many indexes writes more slowly than one with few. Indexes also consume disk space and memory, sometimes more than the table's own data if there are several of them. This is why indexes are added deliberately, based on the queries an application actually runs, rather than indexing every column by default.

A covering index is a special case where an index contains every column a query needs, so the database can answer the query by reading only the index and never touching the underlying table rows at all. This is one of the fastest possible ways to serve a query, because it avoids the extra step of following a pointer from the index back to the full row.

Finally, an index that is never used by any query is pure overhead: it slows down writes and wastes space without ever speeding up a read. Database engines typically expose tools, such as a query planner or an EXPLAIN command, that show whether a given query actually used an available index, which is the standard way to verify that an index is earning its cost.
