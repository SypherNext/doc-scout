Idempotency

An operation is idempotent if performing it more than once has the same effect as performing it exactly once. Calling an idempotent operation five times in a row leaves the system in the same state as calling it a single time. This property matters constantly in distributed systems, because networks are unreliable: a client can send a request, the server can process it successfully, and the response confirming that success can still be lost on the way back. From the client's point of view, a timeout looks identical whether the request never arrived, arrived but was never processed, or was processed perfectly and only the response was lost. The only safe reaction is to retry, and idempotency is what makes retrying safe.

HTTP gives a useful, if imperfect, vocabulary for this. GET, PUT, and DELETE are meant to be idempotent: fetching a resource repeatedly does not change it, setting a resource to a given representation repeatedly leaves it in that same representation, and deleting a resource that is already gone is still "deleted" the second time. POST is traditionally not idempotent, because its whole purpose is often to create something new, and creating something new is exactly the kind of action that should not happen twice. Submitting a payment form is the textbook example: if the confirmation page never loads and the user clicks "submit" again, a non-idempotent payment endpoint can charge the customer twice for one order.

The standard fix for non-idempotent operations like payments or order creation is an idempotency key: the client generates a unique identifier for a single logical attempt, often a random UUID, and sends it with the request, typically in a header. The server records which idempotency keys it has already processed, along with the result of that processing. If a request arrives with a key the server has already seen, the server returns the stored result from the first attempt instead of performing the action again. The client can safely retry the exact same request, with the exact same key, as many times as needed, and the operation will only ever actually happen once.

Idempotency keys need a few supporting decisions to work correctly in practice. The server must store the key and result somewhere durable enough to survive the time window in which retries are expected, often with an expiration so old keys do not accumulate forever. The key must be scoped to a specific operation, since a key that is unique within a general store but misapplied across two different kinds of request could accidentally return the wrong stored result for the wrong action. Choosing a sensible expiration window, long enough to cover realistic retry delays but short enough to avoid unbounded storage growth, is a deliberate design decision rather than an afterthought.

This same idea, making repeated execution safe, comes up far beyond HTTP APIs. Message queue consumers (described separately) often re-receive the same message, database migrations are written so running them twice does no additional harm, and infrastructure tools that describe a desired end state rather than a sequence of steps are idempotent by design: applying the same configuration repeatedly converges to the same result instead of compounding changes.
