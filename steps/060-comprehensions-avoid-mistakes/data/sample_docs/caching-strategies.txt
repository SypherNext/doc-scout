Caching Strategies

A cache stores a copy of data that is expensive to produce so that a later request can be served quickly from the copy instead of redoing the expensive work. The classic motivating example is a database query: computing a result might take 200 milliseconds, but reading the same result from an in-memory cache takes well under a millisecond. The hard part of caching is not storing data, it is deciding what to store, for how long, and what to do when the underlying data changes.

The most common pattern is cache-aside, also called lazy loading. The application first checks the cache for a key. If the key is present, a "cache hit" returns the stored value immediately. If the key is missing, a "cache miss" occurs: the application reads the real value from the source of truth (usually a database), stores it in the cache, and returns it. Cache-aside is popular because the cache only ever holds data that has actually been requested, so memory is not wasted on data nobody reads.

A second pattern is write-through caching. Every time the application writes a value to the database, it also writes the same value to the cache in the same operation. Reads then always hit a cache that is up to date. This trades slightly slower writes for guaranteed fresh reads, which matters for data that must never be stale, such as account balances.

A third pattern is write-back (or write-behind) caching, where writes go to the cache first and are flushed to the database later, often in a batch. This is fast for writes but risks losing data if the cache fails before the flush completes, so it is used only when some data loss is acceptable or when the cache itself is made durable.

Expiration policy is just as important as the write pattern. A time-to-live (TTL) sets a fixed lifetime for each entry; after it expires, the entry is evicted even if it was never invalidated explicitly. TTLs bound how stale data can get without requiring the application to track every place a value might change. When a cache fills up before TTLs expire, an eviction policy decides what to remove. Least Recently Used (LRU) evicts whatever has gone the longest without being read, on the assumption that data accessed recently is likely to be accessed again soon. Least Frequently Used (LFU) evicts whatever has been read the fewest times overall, which handles a small set of very "hot" keys better than LRU but adapts more slowly to shifting access patterns.

Two failure modes come up repeatedly in caching discussions. A "cache stampede" happens when a popular key expires and many requests simultaneously try to recompute it, overwhelming the source of truth; one fix is to let only one request recompute the value while others wait or serve a slightly stale copy. "Cache invalidation" is the general problem of removing or updating cached data the moment the underlying value changes, and is widely considered one of the two genuinely hard problems in computer science, alongside naming things.
