Message Queues

A message queue lets one part of a system hand off work to another part without both parts needing to be available at the same instant. A "producer" places a message onto the queue and moves on immediately. A "consumer" reads messages off the queue, at its own pace, and does the actual work. The queue sits durably in between, holding messages until a consumer is ready for them. This decouples the speed and availability of the producer from the speed and availability of the consumer.

The clearest case for a queue is a slow or unreliable task that should not block the request that triggered it. When a user uploads a video, the web server that receives the upload should not make the user wait while the video is transcoded into several resolutions, a process that might take minutes. Instead, the server places a "transcode this video" message on a queue and immediately tells the user the upload succeeded. A separate pool of worker processes consumes transcoding jobs from the queue whenever they are free. If a worker crashes partway through a job, a well-configured queue returns that message to the queue instead of losing it, so another worker can pick it up.

Queues also act as a buffer that absorbs bursts of traffic. If ten thousand orders arrive in one minute, a system that tries to process every order synchronously can be overwhelmed. A system that places each order on a queue accepts all ten thousand instantly and lets a fixed pool of workers drain the queue steadily over the following minutes, trading a short delay for the order to be processed in exchange for never dropping or rejecting it.

Message delivery guarantees vary and matter a great deal. "At-most-once" delivery means a message might be lost but will never be processed twice; this is rare in practice because it requires accepting data loss. "At-least-once" delivery, the most common guarantee, means a message is never lost but might occasionally be delivered and processed more than once, usually because a consumer crashed after doing the work but before telling the queue it finished. "Exactly-once" delivery, where a message is guaranteed to be processed precisely one time, is the hardest to achieve and the most expensive, and real systems that claim it usually combine at-least-once delivery with deduplication on the consumer side.

Because at-least-once delivery is the common case, consumers are usually written to be idempotent: processing the same message twice should produce the same result as processing it once, for example by using the order ID to check whether that order was already marked as shipped before shipping it again. This single property removes most of the danger of duplicate delivery without requiring a more complex and slower exactly-once system.
