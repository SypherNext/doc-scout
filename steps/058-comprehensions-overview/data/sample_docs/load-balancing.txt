Load Balancing

A load balancer sits in front of a group of servers and decides which server handles each incoming request. The goal is to spread work evenly so that no single server becomes a bottleneck while others sit idle, and to keep the system working when individual servers fail. Without a load balancer, a client would have to know the address of a specific server, which makes it impossible to add, remove, or restart servers without disrupting traffic.

The simplest distribution algorithm is round robin: requests are handed to servers in a fixed rotating order, first server, then second, then third, then back to the first. Round robin is easy to implement and works well when every server has similar capacity and every request costs about the same amount of work. It breaks down when servers differ in capacity or when some requests are far more expensive than others, because a slow server still receives its equal share of requests and falls behind.

Weighted round robin fixes the capacity problem by assigning each server a weight proportional to how much traffic it can handle, so a server with twice the capacity receives twice as many requests. Least connections routing takes a different approach: it sends each new request to whichever server currently has the fewest active connections. This adapts automatically to servers that are temporarily slow, because a slow server accumulates open connections and stops receiving new work until it catches up.

A load balancer also needs to know when a server is unhealthy. Health checks are periodic requests, often a lightweight HTTP endpoint like /health, that the load balancer sends to each server to confirm it is still responding correctly. A server that fails enough consecutive health checks is marked unhealthy and removed from rotation until it recovers. This is what allows a fleet of servers to survive individual crashes without any human intervention: traffic simply stops flowing to the server that went down.

Load balancers are commonly described by which layer of the network stack they operate at. A Layer 4 load balancer makes routing decisions using only transport-level information, such as the source and destination IP address and port, without looking at the content of the request. This is fast but blunt. A Layer 7 load balancer operates at the application layer and can read the actual HTTP request, including the URL path, headers, and cookies, which allows routing decisions like sending all requests for /api/images to one group of servers and /api/search to another, or keeping a given user's requests pinned to the same server, a technique called session affinity or sticky sessions.

Finally, load balancing is not limited to a single tier. Many systems use global load balancing to route a user to the nearest geographic data center, then a local load balancer within that data center to pick a specific server, giving both low latency and fine-grained traffic control at the same time.
