Rate Limiting

A rate limiter restricts how many requests a client can make to a service in a given window of time, for example "at most 100 requests per minute per API key." Its purpose is to protect the service from being overwhelmed, whether by a genuine traffic spike, a bug in a client that retries too aggressively, or a deliberate denial-of-service attempt, and to keep usage fair across many clients sharing the same backend.

The fixed window algorithm is the simplest approach. It divides time into fixed intervals, such as one-minute windows, and counts requests within the current window. Once the count reaches the limit, further requests are rejected until the next window begins. Fixed windows are easy to implement with a single counter per client per window, but they allow a burst problem at the boundary: a client could send its full quota in the last second of one window and its full quota again in the first second of the next window, producing twice the intended rate for a brief moment.

The sliding window algorithm fixes the boundary problem by looking at a window that moves continuously with the current time rather than resetting at fixed points, so it always considers the true number of requests in the last sixty seconds, say, regardless of where that stretch falls relative to clock minutes. This is more accurate but requires tracking individual request timestamps, or an approximation of them, rather than a single counter.

The token bucket algorithm models the limit as a bucket that holds a fixed number of tokens. Each request consumes one token, and if the bucket is empty, the request is rejected. Tokens are added back to the bucket at a steady rate, up to the bucket's capacity. This design naturally allows short bursts, since a client that has not made requests recently has a full bucket and can send a burst immediately, while still enforcing a strict long-run average rate once the bucket is drained. The leaky bucket algorithm is closely related but frames the process in reverse, as requests entering a bucket that drains, or "leaks," at a constant rate, which smooths bursts into a steady outgoing rate rather than permitting them.

When a client exceeds its limit, the service should respond with a clear signal rather than a generic error. The HTTP status code 429 Too Many Requests is the standard response, and well-behaved services include a Retry-After header telling the client how long to wait before trying again. Clients should treat a 429 as a signal to back off, typically with an increasing delay between retries known as exponential backoff, rather than retrying immediately, which would only make the overload worse.

Rate limits can be applied at different scopes depending on what needs protecting: per API key or user account to enforce fair use and billing tiers, per IP address to blunt abuse from a single source, or globally across an entire endpoint to protect a backend resource, such as a database, that cannot scale as quickly as the API layer in front of it.
